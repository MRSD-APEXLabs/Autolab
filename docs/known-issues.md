## Incomplete features (found by tracing the `place` routine end-to-end)

| # | Issue | Where | Workaround |
|---|---|---|---|
| 21 | **`place` never releases the plate.** The *grasp* is real but lives on the Xavier: its servo mode closes the custom Modbus gripper with FSR feedback (see [Xavier](subsystems/xavier.md)); no ROS node ever touches the gripper, and **nothing anywhere opens it at a machine** — the only `gripper_open` is at the start of the next servo run. What `place` actually does: plan to **25 cm above** the target AprilTag (`plan_april_1` = OT-2, `plan_april_2` = shaker, ids hardcoded) → `WAITING_PLACE`, which is literally `std::this_thread::sleep_for(place_wait_s)` returning `true` (10 s, code default — not set in the launch file) → `plan_home_offset` → `SUCCESS`. There is no descent to the deck and no release, and SUCCESS is reported regardless of whether a plate was deposited. The control-flow path is real (the routine executor does see `RUNNING → SUCCESS` on `place_object_status`); the physical place is not. | `manipulation_executive.cpp` (~244–283, 498–519), `move_to_pose_node.cpp` (~787–799) | Open the gripper by hand (joystick **Y**) during the 10 s dwell, or implement a gripper node. The `demo_gripper_bot_controller` in `base_moveit_config_2` exists only for URDF/collision modelling — nothing commands it. |
| 22 | **`pick_wellplate` step can never work.** `step_config.py` publishes `type='pick'`, but the executive accepts only `pick_up` / `place` / `pick_base` / `pick_wellplate`, so the command is logged and dropped. It also watches `behavior/pick_object_status`, while the `"Pick Wellplate"` action publishes `pick_wellplate_status`. Latent — not in the default routine. | `step_config.py` (~38–48), `manipulation_executive.cpp` (~50, ~98–129) | Change the step to `type='pick_wellplate'` and watch `pick_wellplate_status`. |
| 23 | **`test_full_routine.sh` skips its own steps 4–5.** The header promises pick-up + place-into-shaker; the script jumps from `Step 3` to `Step 6`, so the only `place` it exercises is into the OT-2. Its `wait_bt_success()` also treats a *silent* status topic as SUCCESS once RUNNING was seen, masking real failures. | `test_full_routine.sh` (~58–79) | Treat it as an OT-2-only smoke test. |
| 25 | **The default `gcs` container can't talk ROS to the robot.** `gcs` runs on the `autolab_network` bridge while the robot container is `network_mode: host`, and both export `ROS_LOCALHOST_ONLY=1` — so DDS discovery (including `domain_bridge`) never crosses between them. Only `gcs-real` (profiles `hitl`/`deploy`, host-networked) works, and only on the same machine as the robot stack. | `gcs/docker/docker-compose.yaml` (~2–25), `robot/docker/docker-compose.yaml` (~39), `*/docker/.bashrc:13` | `autolab up gcs-real` on the robot machine. |
| 24 | **The planner cannot tell pick from place.** `/task_planner/task_type` (`Move`/`Grasp`/`Place`) is subscribed but **never published** by anything, so it always defaults to `Move` — and even `Place` would change nothing (only `Grasp` is special-cased, for velocity). `placement` and `wellplate_placement` emit byte-identical `plan_april_N` commands. The pick path (`plan_wellplate`) has hardware-tuned X/Y offsets; the place path has none. | `move_to_pose_node.cpp` (~445, ~609–621, ~856–860), `manipulation_executive.cpp` (~498–519) | — |
| 26 | **The planner and the `top_camera` TF are started by the vendored xarm launch — don't start them again.** `planning.launch.xml` includes the team-modified `xarm_ros2/xarm_moveit_config/launch/_robot_moveit_realmove.launch.py`, which spawns `move_to_pose_node` after 15 s (`TimerAction`, line 174) and publishes `world→link_base` and `Chassis_1→top_camera` (`0.012652 0.265518 -0.584171`, ypr `-1.5708 0 1.0472`, lines 226–230; resolves to `world→top_camera = [-0.013, 0.266, 1.477]`). An extra `ros2 run global_planner move_to_pose_node` gives **two planners answering `/planning_command`**. (An earlier version of this page claimed the TF was missing — it isn't.) | `_robot_moveit_realmove.launch.py` (174, 226–230) | Launch `planning.launch.xml` only. |
| 27 | **The OT-2 HTTP wrapper is a separate service that must be running.** `lab_machines.yaml` points at `http://192.168.10.4:8000`; the wrapper's source is `~/ot2-wrapper` on the robot Jetson (FastAPI, port 8000) and is not started by anything in this repo. On 2026-08-31 `192.168.10.4` answered pings but port 8000 was closed. | `lab_machine_executive/config/lab_machines.yaml`, `~/ot2-wrapper/docker/docker-compose.yml` | Start the wrapper where `ot2_base_url` points, or repoint `ot2_base_url`. |
| 28 | **The Xavier perception server exists only on the Xavier.** `autolab@192.168.1.101:~/Autolab-Camera-Edge` (`main.py`, `inspect_cam.py`, `visual_servo.py`, `config.py`, `example_client/test.html`, models).
